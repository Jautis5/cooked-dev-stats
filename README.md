# Cooked Dev social stats

Public statistics for Cooked Dev and Indian Builds. Cooked Dev uses Instagram, TikTok, YouTube, X and Facebook; Indian Builds currently uses Instagram, TikTok, Facebook, X and YouTube. Primary independent dashboard: https://jonass-pandos.github.io/cooked-dev-stats/ . The existing Sites URL remains a mirror. Dashboard source is `site/`; GitHub Pages builds it on source changes and after collector runs. No Codex session or owner computer is required. A hosted 15-minute wait timer chains short publication checks continuously. The next check is queued before the current tick exits; recurring cron and completion-event checks provide backup recovery. GitHub and source-platform outages can still cause delays.

`data/latest.json` holds public observations with a source and timestamp for every metric. `data/posts.csv` and `data/platforms.csv` feed Google Sheets. Failed collection preserves earlier observations and updates the source status; it never fabricates a zero or advances a metric's observation time. Platform view counts are additive plays, not unique cross-platform reach.

Run `python scripts/collect.py` to refresh. Python 3.12 and yt-dlp are required for collection. `python scripts/test_data.py` validates the snapshot. Public pages can withhold metrics or block server requests. Authenticated owner tables can supply additional observations through the bulk browser workflow below; missing values and blocked sessions retain their prior timestamps. The initial registry contained 12 verified videos. New TikTok records are adopted only with an observed owner-matched identity. Existing public posts are refreshed separately.

The owner also uses a bulk browser capture through the already connected Lost Chrome profile. Instagram reel grids and TikTok Studio / Facebook content tables are read together, without opening every video or creating developer apps. Normalized public measurements merge into the correct channel snapshot; rounded labels retain `approximate: true`. The browser-assisted pass requires the owner's computer and extension to be available; the GitHub collector remains independent. Private analytics exports, cookies and account tokens are never included here.

## Autonomous operation and incident recovery

The scheduled run on 20 October 2026 at 10:05 UTC collected real data, but its final Git push failed because the branch advanced during collection. The old workflow discarded those unpublished results when the runner ended. `publish_refresh.py` now fetches the current branch into an isolated disposable worktree, merges metrics by their actual observation times, preserves concurrent source edits and Drive links, then pushes normally. A concurrent push triggers up to four merge/retry attempts. It never force-pushes or resets the caller checkout. Compact public-only recovery snapshots are retained as one-day Actions artifacts. Monthly archives stay in Git instead of being duplicated into every recovery artifact, keeping continuous operation within the free storage allowance. Regression tests recreate the actual two-writer Git race.

`refresh_all.py` isolates channel failures, writes `data/health.json` with the real provider, run link, per-platform updated metric count and latest metric time, and preserves prior values when sources fail. A completed job is not proof that every platform metric is fresh. Instagram and TikTok public extraction and YouTube public metadata can run unattended; individual public requests may still be withheld. Facebook and X currently have no cloud API authorization, so their saved measurements are retained and explicitly marked as requiring authorization. No cookies, browser profiles, passwords or local credentials are uploaded.

`site/` is the dashboard source of truth. `scripts/build_pages.py` bundles that source with current valid fallback data. The Pages workflow runs independently after collection completes (including collection problems, so the status remains visible). The dashboard reads public feeds directly and checks them every five minutes while open. Closing it, Codex, or the owner computer does not stop collection or hosting. `data/health.json` and the Actions run are the live operational evidence.

Local verification: `python -m unittest discover -s scripts -p 'test_*.py'`. Collection: `python scripts/refresh_all.py`. Publish: `python scripts/publish_refresh.py`. Use the GitHub Actions **Refresh public social stats** workflow for a cloud run; a local run is labelled `local_verification`, never reported as a cloud run.

Feed delivery compares the live JSON, the deployed fallback and the last loaded snapshot by their real check dates. Every request uses a fresh cache key; an older CDN response cannot replace a newer bundled or loaded snapshot. The UI distinguishes an unavailable feed from a feed still catching up to a newer verified snapshot.

## Free, unattended mode

### Continuous publication clock

The primary 24-hour path is now `clock.yml`, a chain of short publication checks. Its `social-stats-clock` environment has a hosted **15-minute wait timer**. The successor is queued before the previous workflow exits; no runner stays idle during the wait. Each tick checks for an existing collector before dispatching and then verifies the next clock job by its parent run ID. The collector records `initiator: continuous_clock` and the actual clock run link. Dispatch uses only the job's temporary repository-scoped token. No new account, stored token or paid runner is required. Both the workflow and API guard refuse private-repository operation.

The ordinary cron schedules remain backup. Each clock explicitly invokes the watchdog, with completion events as an additional backup: if a tick fails without handing off, the watchdog recreates the timer; if its successor is already waiting, it does not duplicate it. A waiting job older than 35 minutes can be cancelled and replaced. `continuousClockEnabled: false` stops the successor chain and prevents the watchdog from restarting it. The collection workflow's own cron must also be disabled to pause all collection.

The dashboard reads the actual public clock queue independently from saved metrics. It distinguishes a waiting successor, running tick, missing queue and overdue queue; an unavailable queue API does not hide saved statistics. Every GitHub Pages build versions JS and CSS by their content hash, preventing an older cached program from presenting newer data with old status logic. Apply `python3 scripts/version_assets.py dist` when packaging the Sites mirror.

GitHub's hosted wait timer, Actions API, hosting and the source platforms can still have outages. This removes dependence on recurring cron event delivery; it does not promise impossible zero downtime or access to metrics withheld by a platform.

On 20 October, no scheduled collector or watchdog run was created after the successful on-demand collection at 12:40 UTC. Both workflow definitions were active on the default branch; GitHub reported no general Actions incident. A manually dispatched watchdog at 14:22 UTC correctly detected the stale heartbeat, requested a collector, and saved fresh data at 14:23 UTC. This verifies the recovery code when invoked, not the reliability of the scheduler that must invoke it. The schedules were re-registered with equivalent stepped ranges. This is a mitigation, not evidence of a resolved GitHub scheduling fault. `health.json` now records the actual event trigger, and the UI distinguishes scheduled collection from on-demand collection and labels the 15-minute interval as a target. That cron-based mitigation did not provide a reliable cadence. The continuous wait-timer chain above replaces reliance on cron delivery and is verified by timed cloud runs and actual successor handoffs.

The user requires no new account connections or paid services. Public collection requests run every 15 minutes on GitHub, independent of Codex, Chrome and the owner computer. `data/collection-policy.json` records the policy. The separate **Recover stalled cloud collection** workflow checks at minutes 11, 26, 41 and 56. It does not duplicate a recent active run, uses a 15-minute retry cooldown, recovers overdue/failed collection, and can cancel collector runs stuck beyond 45 minutes before requesting a replacement. It uses only the temporary built-in GitHub Actions token; no new account connection or stored secret is needed. Both schedules depend on GitHub availability and can be delayed. They are not a guaranteed uptime service.

YouTube public channel feeds now discover correctly owned, public new uploads inside the established tracking period and update their available view counts. They never infer a cross-platform match or Drive original. Feed identity is checked using the full channel alternate URL and per-entry channel IDs; YouTube omits the UC prefix from its root feed ID. No feed entries does not imply a new zero. Public feeds can be delayed, bounded or withheld.

Platform access failures do not trigger a retry storm. Facebook, X and other unavailable metrics retain their real observation dates; the interface shows how many accounts actually supplied new metrics. Without additional authorization, the system cannot promise complete private analytics or every platform metric. No OAuth, developer registration, paid API, browser profile or cookie is activated in this mode.

Timed-cloud verification on 20 October 2026: the bootstrap wait timer completed, collector run 39441723947 saved real data at 14:43 UTC, and the production 15-minute successor 39441729130 independently requested collector 39444057021 at 14:58 UTC. That run passed 53 Python tests and the three dashboard suites, saved 116 measured metrics, and queued clock 39444061423 for another 15-minute interval. Completion-event callbacks from token-created runs were not delivered in this test, so publishing and clock audits use explicit workflow dispatches. The manual Verify autonomous delivery workflow exercises both explicit callbacks with the same temporary token permissions, without recollecting data or changing metric dates.
